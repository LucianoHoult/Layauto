# Layauto 开发协作规则

让用户通过 PM 掌握目标与结果，执行和 review 通过仓库记录交接；已有要求内自主推进，新的关键预期和重要变化交给用户决定。

本文件定义开发协作方式。产品行为以 [architecture.md](../architecture.md) 为准；环境操作见 [local-setup.md](../environment/local-setup.md)。用户当前指令决定本轮授权范围，角色名、任务状态或本文件不会扩大授权。

## 1. 文件归属

| 文件 | 唯一职责 |
| --- | --- |
| 根 `AGENTS.md` | 启动、读取入口和少数全局约束 |
| `docs/architecture.md` | 产品行为、边界和工艺解释合同 |
| 本文件 | 角色、推进、验收、上报与交接规则 |
| [task-template.md](task-template.md) | 创建任务时使用的结构，不是实际任务或证据 |
| [roadmap.md](../roadmap.md) | 里程碑、依赖和架构义务的计划归属，不保存逐任务详细状态 |
| [current-work.md](../current-work.md) | 当前节点、任务入口和全局下一步，由 PM 维护 |
| `docs/tasks/Wxxx-目标.md`（有任务时建立） | 一项任务的要求、阶段、决定、执行/review 结果及验收事实 |
| `docs/environment/` | 环境准备、命令、工具运行位置；不定义 PDK 物理语义 |
| `docs/proposals/`、`docs/archive/` | 未采纳方案和历史材料，不作为当前规则 |

任务的详细状态只在任务文件维护；当前入口引用它，路线图引用相关任务。改变产品合同时更新架构正文，改变协作规则时更新本文件；任务记录保留决定及依据，不能靠临时任务决定静默覆盖上层合同。

## 2. 启动与按需读取

可用短指令：`按项目规范，以 PM 角色恢复当前工作。`、`按项目规范，执行 W001。`、`按项目规范，review W001。`

1. 核对仓库路径、branch、HEAD、staged/unstaged/untracked 内容，区分已有改动与本轮产物；先验证记录中的恢复位置确实可访问。
2. 读取根 AGENTS、本文件和目标路径适用的局部 AGENTS；按明确任务编号定位任务，未指定时查看当前入口。不要把磁盘上存在的文件当作已读。
3. 读取任务要求、必要架构原文和现有相关测试；跨模块修改补读接口两侧条款。首次全局规划需梳理完整架构与首版范围，普通恢复不要求重读全量历史对话或无关正文。
4. 对照代码和任务记录，判断哪些结论仍有效、哪些因改动失效，再从下一步继续。编号不存在或有多个候选时说明缺口，不猜测任务和完成状态。

明确要求审阅一组文档或 diff 时可直接按该范围工作，不必制造任务编号。初始化阶段尚无任务文件时，当前入口可暂存首次规范 review 的范围、限制和交接；正式任务建立后使用任务文件。

目录规则只在有局部差异时增加。摘要保留适用范围、关键不变量、失败条件和原文出处；将规范要求、建议、示例、已验证事实与待验证假设区分开。修改行为前阅读对应原条款，摘要不另行定义语义。

## 3. 角色与写入责任

| 角色 | 工作与交付 | 写入归属 |
| --- | --- | --- |
| PM | 核对全局覆盖和依赖，准备任务要求，组织必要方案/代码 review，核验结果、安排下一步并向用户汇报 | 路线图、当前入口；任务阶段、要求、决策和 PM 验收段 |
| 执行 | 调查现状与 legacy 候选，细化必要方案，完成授权代码/fixture/测试/文档；处理 findings，提交证据和下一步 | 任务方案、执行结果及相关产物；不代写 reviewer 结论 |
| Review | 对照架构、输入来源、实际 diff 和证据独立检查；指出可复现问题、影响和验证缺口 | 任务 review 段；默认不修改被审实现，不自行放宽验收 |

角色是职责，不要求每阶段新建会话。关键合同由未承担该变更实现的 reviewer 复核；子 agent 或独立会话都需明确输入、写入范围和交付位置。用户要求新会话 review 时，内部检查不能替代该次 review。

PM 验收须核对要求覆盖、版本、findings 处置及实际证据，可委派专项检查；不能只转述执行摘要。执行者可填写 finding 表的处理列；finding 原文和复核结论由 reviewer 维护。Reviewer 或后续独立复核确认处理结果，保留原 finding 及处置依据。

初期默认串行写入；确有独立边界时使用单独 branch/worktree，并指定集成负责人。共享接口、当前入口和同一任务文件避免并发改写；分支上的记录需随产物一同交接，不能假设其它会话已经看到。

## 4. 规划与推进

首次规划先在路线图覆盖首版能力、必要合同、依赖、未知项和验收节点；只把近期一两项展开到可执行程度。产品未来扩展不能因为架构写得详细就自动进入首版，必要义务也不能因拆包而遗漏。

里程碑按可观察能力验收，执行任务可按模块拆分；基础合同先明确，并尽早接入一个受限但真实的小闭环。缩小能力范围时仍须满足该范围内的不变量和失败语义。Layauto 的 Stage 1–6 是运行时数据流，不是开发会话的阶段编号。

每项任务由 PM 从模板建立；局部步骤、helper 和算法选择留给执行者。涉及共享语义、状态所有权、事务发布或物理解释时，先形成具体方案和必要独立 review。普通文档小修可用简短记录，不要求额外设计文件或新增测试。

任务阶段：`待准备 → 可执行 → 执行中 → 待 review → 待验收 → 已验收`。PM 维护阶段；发现问题回到相应阶段。阻塞原因另列，不用“已完成”掩盖未执行检查。执行者和 reviewer 填写各自交付及下一步，由 PM 接收后推进。

`已验收` 表示满足本任务授权的交付要求；集成状态单独记录。工作区文档交付可验收但仍为未提交/未集成；需要合入目标分支的代码交付须有集成版本和组合验证，才能宣称该交付完成。提交、推送和合并服从用户授权，明确的“不要 commit”也适用于文档记录。

## 5. 验收、事实与上报

| 情况 | 处理 |
| --- | --- |
| 既定要求内的实现选择、测试失败、可逆修复 | 执行与 review 处理，PM 验收后继续，不逐项请用户确认 |
| 可在原目标内解决的技术方案问题 | PM 组织调查、调整和复核，记录理由与影响 |
| 新增或改变输入解释、关键对外格式/行为、能力承诺、验收标准或架构合同 | 先准备具体样本/方案、依据、影响和推荐项，交用户决定 |
| 关键事实缺失、工具/数据不可用，或重复失败影响节点且无法在范围内解决 | PM 说明缺口、已尝试方法、受影响工作及建议；等待必要输入期间推进独立工作 |

“没有与架构原文冲突”不自动授权填补关键语义空白。用户已确认的决定不反复询问；待用户决定的事项不能因等待时间经过或工具输出含糊而自动视为批准。

新的 CDL、报告、绘图、fixture 或 PDK/profile 适配，先调查事实来源、已有样本和 legacy 可取用部分。影响使用预期的未决选择用最小输入/输出、样张或反例交用户判断；既有保真义务由 agent 核验。用户确认使用预期不替代技术正确性检查。

Fixture 记录来源、生成方式、profile、版本和限制。按架构区分 synthetic、tool-captured 与生产验证；真实工具输出保留 raw captures、配置/版本和解析关系。不能用实现自行生成的 golden 作为唯一正确性依据，也不能把未运行工具、未覆盖规则或未知事实汇总为通过。legacy 逻辑取用须符合架构 §11.14，不能引入归档 runtime 依赖。

代码任务按风险执行相关单元、合同、错误路径及组合验证；关键接口首次交付就包含必要失败测试。纯文档变更检查链接、归属、语义和恢复路径，不为凑数量编写测试或运行无关完整回归。

## 6. 证据与交接

执行或 review 记录至少能定位：被测/被审版本，命令和环境，fixture/profile，结果、未执行范围，以及可访问的产物。Review 绑定 base/head 或明确的工作区快照，代码变化后重新检查受影响结论；不机械重跑无关检查。

无 commit 的交接可在同一 checkout 继续，但须记录基线、相关修改/新增/移除文件及身份。需要跨会话复用“已验证”结论时，保留可重建的完整相关快照/补丁和内容标识，覆盖 staged、unstaged 与 untracked；只有文件名清单或 HEAD 不足以证明未提交内容相同。证据身份覆盖被测/被审材料，交接文字不追求包含自身的最终 hash。

每个有意义的交付或中断前更新一次恢复点、问题和下一步；不保存逐轮思考流水账。旧决定及 review 处理理由可追溯，长日志以链接保存。临时目录只能用于本机短期交接，跨主机前按授权保存可访问版本；不能把本地未提交文件或虚拟环境假设为云端已有。

## 7. PM 对用户的接口

常规更新约 100–200 字，必要证据用链接展开。保留不确定性、未验证项及 review 分歧；字数是阅读目标，不得靠删掉重要限制满足。用户通常无需阅读执行/review 原始记录。

```text
当前节点：现在要完成的能力。
预期与结果：本轮实际交付，必要时附代表产物。
核验范围：验证到哪里，尚有什么限制。
变化/待决：无，或需要用户决定的具体新预期、影响和推荐项。
下一步：继续什么；需新会话时给角色、任务编号和一句启动指令。
```

PM 与下层以任务文件交接。用户通知“W001 执行结束”只是触发 PM 核验，不构成验收证据；PM 读取结果、安排 review/修复后再推进。每个里程碑给一次代表结果，供用户判断整体方向。

## 8. 第一版的使用与演练

先用当前入口指定的规范 review 检查读取和交接是否闭合，再正式建立路线图与任务。验证点是：一个新会话能找到范围、适用条款、待审材料、授权限制和下一步，且能区分旧改动、假设与已验证结果。没有进行过真实新会话恢复时，如实标为未演练。

仅在实际任务暴露需要后拆分角色文件、增加局部 AGENTS 或自动化检查。写了规则文件不代表会自动创建会话、调度后台任务或同步状态。

读取机制参考：[OpenAI AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)（2026-09-08 查阅）。本项目要求修改前显式检查适用局部规则；不依赖从根目录递归自动加载全部规则。
